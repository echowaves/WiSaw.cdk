3. What code touches a photo's deletion lifecycle, from user request through database row to S3 objects?

Three separate chains touch it; the app only runs the first, and the third is what actually removes S3 bytes.

Chain 1 — user request → DB soft delete (no S3 call anywhere in this chain). The GraphQL surface declares deletePhoto(photoId: String!, uuid: String!): String! (graphql/schema.graphql:401 (Mutation.deletePhoto) @ 3813371); the resolver factory binds that field to the single AppSync Lambda data source with no mapping-template args (lib/resources/resolvers.ts:40 (createResolvers) @ 3813371, lib/resources/resolvers.ts:72-77 (createResolvers) @ 3813371). The monolithic lambda dispatches on event.info.fieldName and calls handler.resolver(...handler.getArgs(event.arguments)) (lambda-fns/index.ts:375-383 (exports.main) @ 3813371); the deletePhoto entry maps args to [photoId, uuid] (lambda-fns/index.ts:269 (deletePhoto) @ 3813371). The controller asserts both ids, runs a frozen-wave check, and then performs a soft delete only — UPDATE "Photos" SET "active" = false WHERE id = $1, the row survives, there is no rowcount check, and it returns 'OK' even when zero rows matched (lambda-fns/controllers/photos/delete.ts:7 (main) @ 3813371, lambda-fns/controllers/photos/delete.ts:35 (main) @ 3813371). It then recounts the first affected wave (lambda-fns/controllers/photos/delete.ts:42 (main) @ 3813371), and _updatePhotosCount recomputes Waves.photosCount/updatedAt/freezeDate from rows filtered by "active" = true, so the soft-deleted photo drops out of wave counts (lambda-fns/controllers/waves/_updatePhotosCount.ts:4 (_updatePhotosCount) @ 3813371). The flag itself is exposed on the Photo type (graphql/schema.graphql:27 (Photo.active) @ 3813371).

4. How does scripts/cleanup-s3.js classify and delete S3 keys?

Classification. The whole reconciliation is one pure function, classifyKey(key, activeIds) => 'keep' | 'delete' | 'report', documented by a rule-table comment: media uuid.*/uuid-thumb.webp whose DB row is gone → delete; seo/<uuid>.json sidecar whose row is gone → delete; sidecar of an active photo → keep; anything else (including seo/_last-run.json and junk) → report only, never delete — the comment records that "the old code deleted every non-UUID key, which took out all ~22k sidecars and the watermark" (scripts/cleanup-s3.js:27 (classifyKey) @ 3813371). Implementation order: first test SIDECAR_KEY_RE, a strict lowercase-UUID seo/<uuid>.json pattern; a match returns 'keep' if the UUID is in activeIds, else 'delete'; otherwise extractPhotoId extracts a lowercase-UUID prefix (anchored at ^ — no delimiter or extension required) and returns keep/delete on membership; a key with neither shape returns 'report' (scripts/cleanup-s3.js:19 (SIDECAR_KEY_RE) @ 3813371, scripts/cleanup-s3.js:21 (extractPhotoId) @ 3813371, scripts/cleanup-s3.js:33 (classifyKey) @ 3813371). A consequence visible in code: uppercase-UUID keys never match either regex and are always 'report'. The sidecar-key contract is the writer's — sidecarKey(id) lowercases, and cleanup-s3's comment names it; non-UUID ids written through it produce keys that miss SIDECAR_KEY_RE and land in 'report' (lambda-fns/utilities/seoSidecar.ts:115 (sidecarKey) @ 3813371, scripts/cleanup-s3.js:15 (header comment) @ 3813371). The active set is SELECT "id" FROM "Photos" WHERE "active" = true collected into a Set (scripts/cleanup-s3.js:58 (getPhotoIds) @ 3813371). The driver loops all listed keys through the classifier — 'delete' → toDelete, 'report' → reported (surfaced in logs, first five printed, never deleted), 'keep' falls through (scripts/cleanup-s3.js:150 (main) @ 3813371). All keys come from full-bucket ListObjectsV2 pagination via ContinuationToken, collecting only Key (scripts/cleanup-s3.js:94 (getS3Objects) @ 3813371).

Deletion. Deletion is a sequential for…of loop issuing one DeleteObjectCommand({ Bucket, Key }) per key with await — no batch DeleteObjects, no concurrency (scripts/cleanup-s3.js:187 (main) @ 3813371). Dry-run never deletes: --dry-run sets the flag and, when toDelete is non-empty, prints a header and exits before the delete loop; the per-key print is commented out so dry-run shows only counts (scripts/cleanup-s3.js:120 (main) @ 3813371, scripts/cleanup-s3.js:180 (main) @ 3813371). npm entry points are cleanup-s3 and cleanup-s3:dry-run (package.json:19-20 (scripts) @ 3813371). The bucket is config.S3_BUCKET || wisaw-img-${env} and the S3 client region is hardcoded us-east-1 (scripts/cleanup-s3.js:119 (main) @ 3813371).

Checks on the classify→delete path that reject a value or throw. getPhotoIds wraps connect+query in a 15 s Promise.race timeout rejecting with "Database connection timeout"; the catch does not rethrow — it degrades to an empty Set and announces LIST-ONLY mode (scripts/cleanup-s3.js:73 (getPhotoIds) @ 3813371, scripts/cleanup-s3.js:87 (getPhotoIds) @ 3813371). An empty active set — DB failure or genuinely zero active photos, indistinguishable — short-circuits at photoIds.size === 0: log the object count, optionally print ten keys in dry-run, and exit before any classification or deletion (scripts/cleanup-s3.js:133 (main) @ 3813371). extractPhotoId returns null rather than throwing on non-match, and classifyKey maps that to 'report' — the reject-instead-of-delete guard (scripts/cleanup-s3.js:24 (extractPhotoId) @ 3813371, scripts/cleanup-s3.js:40 (classifyKey) @ 3813371). Per-key delete failures are caught, logged ("Failed to delete"), and skipped; the loop continues and the run still ends "Cleanup complete" (scripts/cleanup-s3.js:191 (main) @ 3813371). An unknown env is not rejected — it falls back to dev config (scripts/cleanup-s3.js:48 (loadEnvConfig) @ 3813371); a missing .env.<env> module lands in main().catch(console.error) and the finally still exits 0, so the exit code is 0 even on failure (scripts/cleanup-s3.js:200 (main) @ 3813371). The header claims the module is require()-able without side effects; that holds for env config, S3 client, and DB — all inside main — but the RDS CA certificate is read with fs.readFileSync at module load (scripts/cleanup-s3.js:4 (header comment) @ 3813371, scripts/cleanup-s3.js:13 (top-level require) @ 3813371).
