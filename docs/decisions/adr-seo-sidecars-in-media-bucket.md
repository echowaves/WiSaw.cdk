# ADR: Publish per-photo SEO sidecar JSON to the media bucket because Lambda@Edge cannot reach Postgres

Date: 2026-11-06
Decision shown by: `49f8013` "feat(seo): publish and read per-photo SEO sidecars at the edge"
Status: accepted (recorded after the fact; approved by the user on 2026-11-06)

Lambda@Edge cannot join a VPC, so it cannot reach Postgres for the caption, labels, and place that make a photo page rankable — before this decision every one of the ~21k indexed pages rendered the placeholder title "wisaw photo \<uuid\>". We decided to denormalize: `generateSiteMap` copies those fields into `seo/<id>.json` objects next to the media in the `wisaw-img-<env>` bucket (key contract `sidecarKey()` lowercases the id), publishing incrementally for photos touched within a lookback window, bounded by a watermark (`seo/_last-run.json`) plus a 5-hour schedule, with a one-off backfill script for already-indexed URLs; the edge injector reads that object — S3 API, in-memory cache, fail-open to an un-enriched page on any miss or error — to build real titles, descriptions, alt text, and JSON-LD structured data. We accepted bounded staleness (`CacheControl: max-age=60` on the sidecar plus the reader's own 10-minute cache) in exchange for per-photo text at the edge at all, and accepted that page SEO now depends on an S3 object contract shared by two writers (scheduled publisher, backfill script), an edge reader, and the cleanup-s3 reconciler — deleting or reshaping `seo/<id>.json` keys breaks indexed pages silently, so changes to the key or body shape must move all four parties together.
